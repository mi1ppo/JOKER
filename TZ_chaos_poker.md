# ТЗ: «Chaos Poker» (рабочее название)

Веб-игра в покер для компании друзей: Техасский Холдем + карты событий, способности, побочные ставки, судья (человек или ИИ), задания с фото и физическая активность. Игроки подключаются к игре с телефонов по QR-коду, сервер работает на ноутбуке.

---

## 0. Как работать с этим документом (инструкция для Copilot)

1. Реализуй проект **строго по этапам** из раздела 17. Не переходи к следующему этапу, пока не проходят тесты и критерии приёмки текущего.
2. Вся игровая логика (`app/game/`) должна быть **чистым Python без сетевого ввода-вывода**, чтобы её можно было тестировать без сервера.
3. Всё, что не описано явно, реализуй самым простым способом и оставь комментарий `# TODO: уточнить`.
4. Тексты интерфейса и игровых событий: **на русском языке**. Код, имена переменных, комментарии к коду: на английском.
5. Никакой базы данных: состояние комнаты хранится в оперативной памяти сервера.

---

## 1. Концепция

- База: Texas Hold'em No-Limit, 2–8 игроков.
- Поверх базы: **Карты Событий** (правило меняется на одну раздачу), **Способности** (одноразовые умения игроков), **Побочные ставки**.
- **Судья (диллер)** ведёт игру: человек со своим телефоном, ИИ через API или отсутствует.
- **Задания:** штрафы, фото-задания (в том числе сгенерированные ИИ), физические активности с использованием датчиков телефона.
- Управление с телефонов: главный телефон (host) показывает общий стол, игроки видят личные данные на своих телефонах.

## 2. Технологии и окружение

| Компонент | Выбор |
|---|---|
| Язык | Python 3.11+ |
| Веб-фреймворк | FastAPI + uvicorn |
| Реальное время | WebSocket (встроенный в FastAPI) |
| Валидация данных | pydantic v2 |
| Клиент | статические HTML + vanilla JS + CSS (без сборки, без фреймворков), mobile-first |
| QR-коды | библиотека `qrcode` (генерация PNG на сервере) |
| Обработка фото | Pillow |
| ИИ | GigaChat API через интерфейс `LLMClient`, собственный клиент на `httpx` с автоматическим обновлением токена (раздел 15) |
| HTTP-клиент | httpx (async) |
| Тесты | pytest |

**Окружение:**
- Сервер запускается на **ноутбуке**, все телефоны в **одной Wi-Fi сети**.
- Обязателен **HTTPS** (иначе камера и датчики движения в браузере не работают). Скрипт `run.py` при старте должен:
  1. определить локальный IP ноутбука;
  2. использовать сертификат из `certs/` (создаётся через `mkcert` или самоподписанный, инструкция в README);
  3. запустить uvicorn на `0.0.0.0:8443`.
- Все адреса в QR-кодах строятся как `https://<LAN_IP>:8443/...`.
- В README описать: как открыть порт в файрволе, как установить корневой сертификат на телефоны, альтернатива через туннель (Cloudflare Tunnel / ngrok).
- Для ИИ-судьи нужен интернет на ноутбуке и **корневой сертификат Минцифры** в `certs/russian_trusted_root_ca.pem` (без него запросы к GigaChat не пройдут проверку). В README описать, где взять сертификат и ключ авторизации GigaChat (раздел 15.1).

## 3. Роли и подключение

**Роли:** `host` (главный телефон, админ), `dealer` (судья, необязательный), `player`.

### 3.1. Порядок подключения

1. **Host** открывает `https://<LAN_IP>:8443/host` на главном телефоне и нажимает «Создать игру». Сервер создаёт комнату и генерирует два одноразовых токена (`secrets.token_urlsafe(16)`): для диллера и для игроков.
2. **Шаг «Диллер»:** на экране host показывается QR-код №1 (ссылка `/dealer?token=...`). Ниже кнопки: «Играем без диллера» и «Диллер-ИИ».
3. Диллер сканирует QR, вводит имя. У host статус «Диллер подключён». QR-код №1 сразу становится недействительным.
4. **Шаг «Игроки»:** host показывает QR-код №2 (ссылка `/play?token=...`) и список подключившихся в реальном времени.
5. Игрок сканирует QR, вводит имя, выбирает цвет/аватар-эмодзи и ставит галочку согласия (камера, показ фото на общем экране, датчики движения).
6. Host нажимает «Начать игру» (минимум 2 игрока). После старта QR-код №2 отключается, если в настройках не включено «Подключение в ходе игры».

### 3.2. Режимы диллера

| Режим | Описание |
|---|---|
| `human` | Отдельный телефон судьи, панель управления (раздел 8.1) |
| `ai` | Судья-ИИ (раздел 8.2) |
| `none` | Без диллера, задания подтверждаются голосованием игроков |

### 3.3. Переподключение
Каждый участник получает `session_token`, который сохраняется в `localStorage`. При обрыве связи клиент автоматически переподключается и получает актуальный снимок состояния. Место игрока сохраняется до конца игры; ход игрока, который отключён, обрабатывается по таймеру (авто-fold).

## 4. Правила игры (база)

- **Стартовый стек:** 1000 фишек (настройка).
- **Блайнды:** старт 10/20. Повышение каждые 8 раздач (настройка) по шкале: 10/20, 20/40, 40/80, 75/150, 100/200, 150/300, 200/400, 300/600.
- **Кнопка дилера** (позиция, не путать с ролью диллера) переходит по часовой стрелке. В игре 1 на 1 кнопка = малый блайнд и ходит первой префлоп.
- **Раздача:** каждому по 2 карты; торги: префлоп → флоп (3 карты) → тёрн (1) → ривер (1) → шоудаун.
- **Действия:** fold, check, call, raise, all-in. Минимальный рейз равен размеру предыдущего повышения (не меньше большого блайнда).
- **Таймер хода:** 45 секунд (настройка). По истечении: check, если можно, иначе fold. Таймер работает на сервере.
- **Побочные банки** (side pots) при all-in считаются стандартно; нечётная фишка отдаётся первому игроку слева от кнопки.
- **Комбинации:** стандартные. Оценка руки из 7 карт (2 + 5) в `evaluator.py`, вернуть сравнимый кортеж ранга.
- **Выбывание:** игрок с 0 фишек выбывает и остаётся в игре зрителем. Игрок, выбивший его (забравший основную часть банка), получает 1 способность.
- **Конец игры:** остался один игрок, либо host завершил игру, либо достигнут лимит раздач (если задан). После этого формируется итог (раздел 13).

## 5. Карты Событий

**Одно событие на раздачу.** Событие выбирается перед раздачей карт в фазе `EVENT_REVEAL`. Частота зависит от «Уровня хаоса» (раздел 12).

**Окно вето:** после показа события 8 секунд, в течение которых игрок со способностью «Вето» может его отменить. Затем событие применяется.

Каталог хранится в `data/events.json`, каждая запись: `id`, `title`, `description`, `weight`. Реализация эффектов в `app/game/events.py` через хуки движка (`on_hand_start`, `modify_blinds`, `on_after_deal`, `on_reveal_flop`, `compare_hands`, `on_showdown`).

| id | Название | Эффект |
|---|---|---|
| `mirror` | Зеркало | На шоудауне побеждает **худшая** комбинация (сравнение инвертируется) |
| `double_stakes` | Двойной кон | Блайнды ×2 на эту раздачу, минимальный рейз соответственно ×2 |
| `spy` | Шпион | После раздачи одна случайная карта случайного не сфолдившего игрока открывается всем |
| `carousel` | Карусель | Каждый выбирает одну карманную карту (15 сек, по умолчанию случайная) и передаёт её игроку слева |
| `blind_flop` | Слепой флоп | Флоп лежит рубашкой вверх и открывается только на шоудауне; тёрн и ривер открываются как обычно |
| `wealth_tax` | Налог на богатых | Игрок с самым большим стеком отдаёт 10% стека игроку с самым маленьким (округление вниз) |
| `joker` | Джокер | Одна случайная общая карта (определяется при её открытии) становится джокером: каждый игрок на шоудауне использует её как любую нужную ему карту |

Событий можно добавлять новые: все эффекты должны быть реализованы в коде, ИИ-судья не изобретает новые механики (раздел 8.2).

## 6. Способности

Каталог: `data/abilities.json`, реализация: `app/game/abilities.py`.

**Выдача:**
- в начале игры каждому по 2 разные случайные способности;
- +1 за каждые 5 раздач;
- +1 за выбывание соперника;
- в руке максимум 3 способности.

**Правила использования:** одноразовые; доступны только не сфолдившим игрокам во время раздачи; не более одной способности от игрока за один круг торгов; использование объявляется на host («Аня использовала Заморозку на Диму»).

| id | Название | Эффект |
|---|---|---|
| `peek` | Подглядеть | Игрок выбирает соперника и видит **одну случайную** его карманную карту (только он) |
| `redraw` | Пересдача | Заменить одну свою карманную карту новой из колоды (до ривера) |
| `veto` | Вето | Отменить Карту События в окне вето (только в этом окне) |
| `freeze` | Заморозка | Выбранный соперник в текущем круге торгов не может рейзить (all-in допустим, только если он не превышает call) |
| `steal` | Воровство | Забрать 5% стека выбранного игрока (не all-in игрока, максимум до его стека, до ривера) |

## 7. Побочные ставки

- До флопа (в фазе `PREFLOP` перед первым действием) любой игрок может поставить **1 большой блайнд** на одно из утверждений, выбранных сервером для этой раздачи из списка:
  - «Среди общих карт будет пара»;
  - «Флоп будет одной масти (три одинаковые)»;
  - «Победит игрок X»;
  - «Дойдём до шоудауна (никто не выиграет без вскрытия)».
- Ставки собираются в отдельный **пул побочных ставок**. По итогам раздачи угадавшие делят пул поровну. Если никто не угадал, пул добавляется в основной банк.
- Одна побочная ставка на игрока за раздачу. Побочные ставки отключаются на низком уровне хаоса.

## 8. Судья (диллер)

### 8.1. Судья-человек (`human`)
Отдельный экран `/dealer`. **Не играет и не видит карманные карты игроков.** Возможности:
- вручную запустить событие (выбрать из каталога или случайное) в начале следующей раздачи;
- выдать задание игроку (штраф или бонус): свой текст, из заготовленного банка или сгенерированное ИИ;
- выдать фото-задание (раздел 9.2);
- принять или отклонить выполнение любого задания;
- вынести **Указ** (не чаще, чем раз в 5 раздач, настройка):
  - `bets_multiple_of_bb`: все ставки кратны большому блайнду;
  - `raise_cap`: не более 2 рейзов за круг;
  - `silence`: запрет разговоров о картах (штраф 1 BB за нарушение, судья нажимает «Штраф» на игрока);
  - свободный указ: только текст, объявляется на host, без эффекта на движок;
- поставить игру на паузу; назначить штраф в фишках любому игроку (до 2 BB за раз).

### 8.2. Судья-ИИ (`ai`)
ИИ вызывается через `LLMClient` (раздел 15). Функции:
- **Комментарии:** после каждой раздачи 1–2 предложения (спортивный комментатор, подкалывает игроков), выводятся на host, при желании озвучиваются через `speechSynthesis` браузера.
- **Выбор события:** ИИ выбирает событие **только из каталога** `events.json` и добавляет своё пояснение под ситуацию. Придумывать новые механики ИИ не может.
- **Штрафы и текстовые задания:** генерирует под контекст игры и настройки компании.
- **Взятки:** игрок предлагает N фишек судье и выбирает, что хочет (подсказка о раздаче, замена события). ИИ возвращает решение `{accepted, effect, comment}`; принимать взятку он не обязан. Фишки в любом случае уходят в основной банк следующей раздачи.
- **Итоговый протокол вечера** с номинациями (Главный блефер, Самый удачливый, Главный жертва судьбы и т.п.).
- **Ограничение (v1):** фото-задания в режиме `ai` **недоступны**, кнопка скрыта. ИИ-проверка фото не реализуется.

### 8.3. Режим без диллера (`none`)
События выбираются случайно, штрафы и физические задания подтверждаются большинством голосов остальных игроков, фото-задания отключены.

## 9. Задания

### 9.1. Штрафы и бонусные задания
- **Штраф** получает игрок, проигравший больше всего фишек в раздаче, если банк ≥ 10 BB (порог настраивается). Режим включается в лобби.
- **Бонусное задание** предлагается добровольно за награду в фишках. Отказаться от штрафа можно, заплатив 2 BB.
- Источники текстов: банк `data/fallback_tasks.json` (минимум 40 заданий трёх уровней остроты: мягкий, средний, острый), ИИ или судья.

### 9.2. Фото-задания (только режим `human`)
Порядок:
1. Диллер нажимает «Выдать фото-задание», выбирает игрока (или случайного), тип (штраф/бонус), сложность.
2. Сервер получает задание: генерация ИИ или из банка.
3. Задание (текст и таймер) показывается **на host** и на телефоне игрока. У игрока открывается экран камеры.
4. Игрок делает снимок через `<input type="file" accept="image/*" capture="environment">` (для селфи `capture="user"` по типу задания) и загружает его на сервер.
5. Фото уходит **диллеру**. Он видит его и нажимает «Принять» или «Отклонить».
6. При принятии: штраф снят, бонус начислен, фото на 8 секунд показывается на host, остальные игроки ставят реакции-эмодзи. При отклонении: повторная попытка (одна) или штраф 2 BB.

**Задания генерирует ИИ.** Требования к запросу:
- предмет или действие должны быть выполнимы в обычной квартире;
- без опасных действий (высота, огонь, острые предметы), без выхода из квартиры;
- без задач, требующих чужой личной информации;
- уровень остроты задаётся настройками лобби.

Формат ответа ИИ (JSON): `{"title": str, "description": str, "time_limit_sec": int, "camera": "front"|"back", "difficulty": 1|2|3}`.
Примеры: «Найди самый старый предмет в квартире и сфотографируй его с собой», «Сфотографируй что-то, что можно надеть на голову вместо шляпы», «Собери в кадре три предмета одного цвета».
Если ИИ недоступен (нет ключа, ошибка, таймаут 8 секунд), берём задание из банка `data/fallback_tasks.json` (не менее 25 фото-заданий).

**Дополнительные форматы (реализовать на позднем этапе):**
- «Фото-блеф»: игрок делает селфи, остальные голосуют, сильная или слабая у него рука, угадавшие получают бонус;
- «Фото-взятка»: смешное фото вместо фишек для судьи-человека.

### 9.3. Физические активности
Опциональны, настраиваются в лобби: интенсивность `off | light | medium | hard`. Датчики через `DeviceMotionEvent` (на iOS нужен `DeviceMotionEvent.requestPermission()`, вызывать только по нажатию кнопки).

| Активность | Как работает |
|---|---|
| Шейк-баттл | Двое трясут телефон 10 секунд, побеждает набравший больше «энергии» (сумма модулей ускорения), приз: бонусные фишки |
| Замри | По сигналу все замирают на 5 секунд, телефон фиксирует движение, дёрнувшиеся платят 1 BB |
| Приседания/отжимания (штраф) | Телефон в руке или в кармане, подсчёт повторений по пикам ускорения, порог задаётся в настройках; запасной вариант: подтверждение судьи или голосование |
| Стоячий стол | Проигравший раздачу играет следующую стоя (без автоматической проверки, отметка судьи) |
| Дуэль | Два игрока играют в «камень-ножницы-бумага» на фишки, результат вводят кнопками на телефонах |

Если датчики недоступны или разрешение не получено, активность подтверждается вручную судьёй (или голосованием в режиме `none`). Любую активность можно пропустить за небольшой штраф в фишках.

## 10. Видимость данных

Правило: **публичное идёт на host и всем, личное только владельцу.** Сервер собирает для каждого соединения свой снимок состояния и **никогда не отправляет чужие карманные карты**, скрытые карты флопа в `blind_flop` и т.п.

| Информация | Host | Игрок | Диллер |
|---|---|---|---|
| Общие карты (флоп, тёрн, ривер) | да | да | да |
| Банк, ставки, стеки, чей ход | да | да | да |
| Карта События | да | да | да |
| Выданные задания, таймеры | да | да | да |
| Принятые фото и реакции | да | да | да |
| Комментарии и указы судьи | да | да | да |
| Карманные карты | нет | только свои | нет |
| Способности игрока | нет (только объявление использования) | только свои | нет |
| Результат «Подглядеть» | нет | только получатель | нет |
| Фото на проверке | нет | автор | да |
| Шоудаун | да | да | да |
| Панель управления игрой | да | нет | нет (у диллера своя панель) |

## 11. Экраны

### 11.1. Host (`/host`) — общий стол
- Лобби: QR-код диллера, QR-код игроков, список игроков, настройки, кнопка «Начать игру», индикатор статуса ИИ-судьи и кнопка «Проверить ИИ» (раздел 15.4).

### 11.4. Оформление карт (рисуются кодом, без картинок)

Все карты отрисовываются **на клиенте средствами HTML/CSS** (допустим inline SVG). Файлы с изображениями колоды не используются.

**Модули:** `static/js/cards.js` (функция `renderCard(card, {size, faceDown, highlight})` возвращает DOM-элемент) и `static/css/cards.css`.

**Формат карты в протоколе и в состоянии:** строка из двух символов: ранг (`2`–`9`, `T`, `J`, `Q`, `K`, `A`) + масть (`s` пики, `h` червы, `d` бубны, `c` трефы). Примеры: `"As"`, `"Td"`, `"7c"`. Скрытая карта передаётся как `null`. Сервер (`cards.py`) и клиент используют один и тот же формат. Ранг `T` отображается как «10».

**Лицо карты:**
- светлая карточка со скруглёнными углами, пропорции 5:7;
- ранг и масть в левом верхнем углу и те же, перевёрнутые, в правом нижнем;
- крупный символ масти по центру (♠ ♥ ♦ ♣ через Unicode или SVG);
- для J, Q, K и туза без портретов: крупная буква и масть по центру.

**Цвета мастей:**
- классический режим: пики и трефы чёрные, червы и бубны красные;
- **четырёхцветный режим** (настройка лобби): пики чёрные, червы красные, бубны синие, трефы зелёные.

**Рубашка:** единая для всех карт, рисуется CSS (градиент + повторяющийся геометрический узор), цвет задаётся CSS-переменной темы.

**Размеры:** через CSS-переменную `--card-w` и относительные единицы. Крупные карты на host (общие карты стола), средние у игрока (его карманные карты), мелкие для показа рук на шоудауне. Интерфейс рассчитан на портретную ориентацию телефона.

**Анимации** (только CSS, не длиннее 500 мс каждая):
- раздача: карта «прилетает» от колоды к игроку;
- переворот при открытии (`rotateY`): флоп открывается по одной карте с задержкой 200 мс, затем тёрн и ривер;
- подсветка карт победившей комбинации на шоудауне;
- лёгкая тряска экрана при появлении Карты События.

**Особые состояния карт:**
- «Слепой флоп»: карты флопа лежат рубашкой вверх с меткой «?», переворачиваются на шоудауне;
- «Джокер»: золотая рамка и значок ★, эффект при определении карты-джокера;
- «Шпион»: открытая карта подсвечивается с подписью «Шпион»;
- «Карусель»: анимация перелёта передаваемой карты к соседу;
- «Пересдача»: старая карта «сгорает», новая появляется с анимацией переворота.

**Карты События и Способностей** оформляются отдельно от игральных карт: карточка с рамкой, эмодзи-иконкой, названием и коротким описанием. Цвет рамки по типу: события красно-оранжевые, способности сине-фиолетовые. Способности игрока показываются рядом с его картами, использованные становятся серыми.

**Доступность:** у каждой карты есть `aria-label` («Туз пик»); в четырёхцветном режиме масти различаются не только цветом, но и символом.

## 15. Интеграция с ИИ (GigaChat)

### 15.1. Провайдер и настройки

Провайдер: **GigaChat API** (Сбер). Реализация: собственный тонкий клиент на `httpx` (async), без официального SDK (меньше зависимости от версий библиотеки). Остальное приложение зависит только от интерфейса `LLMClient`, поэтому провайдера при желании можно заменить.

```python
class LLMClient(Protocol):
    async def generate_json(self, system: str, user: str, schema: dict, *,
                            priority: str = "high", max_tokens: int = 400) -> dict: ...
    async def generate_text(self, system: str, user: str, *,
                            priority: str = "high", max_tokens: int = 200) -> str: ...
```

Оба метода бросают `LLMUnavailable`, если ответ получить не удалось. Вызывающий код **обязан** перейти на резервный контент из `data/`.

**Файл `.env.example`:**

```
GIGACHAT_AUTH_KEY=                 # Authorization key (Base64 от Client ID:Client Secret), показывается один раз
GIGACHAT_SCOPE=GIGACHAT_API_PERS
GIGACHAT_OAUTH_URL=https://ngw.devices.sberbank.ru:9443/api/v2/oauth
GIGACHAT_API_BASE=https://api.giga.chat/v1
GIGACHAT_MODEL=GigaChat-2          # актуальный список: GET /models
GIGACHAT_CA_BUNDLE=certs/russian_trusted_root_ca.pem
GIGACHAT_VERIFY_SSL=true           # false только для отладки, при старте выводится предупреждение
GIGACHAT_TOKEN_BUDGET=200000       # лимит токенов на одну партию (0 = без лимита)
```

Правила:
- **Access token в `.env` не хранится**, сервер получает и обновляет его сам (раздел 15.2).
- Если `GIGACHAT_AUTH_KEY` пустой, ИИ-функции отключены: игра идёт на резервном контенте, а режим «Диллер-ИИ» в лобби показывает подсказку, как настроить ключ.
- Реальный ключ хранится только в `.env` (он в `.gitignore`). В README описать, где взять ключ в личном кабинете GigaChat API.

### 15.2. TokenManager: автоматическое обновление токена

Access token живёт **30 минут**. Цель: запросы к ИИ **не ждут получения токена** в обычной работе. Обновление происходит заранее, в одном экземпляре и без лишних запросов. Модуль: `app/dealer/token_manager.py`.

**Три уровня защиты:**

1. **Упреждающее обновление (основной механизм).** Фоновая задача запускается при старте сервера (`lifespan`) и обновляет токен за `REFRESH_MARGIN = 120` секунд до истечения (со случайным разбросом до 10 секунд). В обычной ситуации `get_token()` ничего не ждёт: токен уже в памяти (быстрый путь без сети и без блокировки).
2. **Ленивая страховка.** Если токена нет или до конца осталось меньше `HARD_MARGIN = 30` секунд, `get_token()` сам запускает обновление.
3. **Реактивное обновление при 401.** Если API ответил 401, клиент вызывает `invalidate(использованный_токен)`, получает новый токен и повторяет запрос **один раз**.

**Обязательные свойства:**
- **Single-flight:** сколько бы вызовов ни ждали токен одновременно (в том числе получивших 401), к OAuth уходит **один** запрос, остальные используют его результат (`asyncio.Lock` и повторная проверка после захвата блокировки).
- **Защита от шторма 401:** `invalidate(bad_token)` помечает токен устаревшим, только если он всё ещё текущий. Если его уже заменили, лишний запрос не делается.
- **Нормализация `expires_at`:** значение приводится к секундам (если число больше `1e11`, это миллисекунды, делим на 1000). Если значение выглядит некорректным (в прошлом или дальше чем через час), токен считается действительным 25 минут с момента получения.
- **Уникальный `RqUID`:** `uuid4` на каждый запрос токена.
- **Быстрый отказ:** после неудачного обновления в течение `COOLDOWN = 5` секунд новые попытки не выполняются, `get_token()` сразу бросает `TokenUnavailable`. Игра не ждёт, а сразу берёт резервный контент.
- **Повторы в фоне:** при ошибке фоновая задача повторяет попытки с паузой 5, 10, 20, 40, 60 секунд (потолок 60). Пока старый токен действует, игра работает как обычно.
- **Один общий `httpx.AsyncClient`** для OAuth и API (keep-alive, пул соединений, `verify=<CA-файл Минцифры>`), а не новое соединение на каждый запрос. Таймауты OAuth: connect 4 с, общий 10 с.
- **Простой (опционально):** если ИИ не использовался 15 минут и нет комнат с ИИ-функциями, фоновая задача пропускает обновления. При возврате (выбор режима «Диллер-ИИ», кнопка «Проверить ИИ») токен прогревается заранее (`warm_up()`).
- **Секреты:** ни ключ, ни токен не пишутся в логи, тексты исключений и `repr`. В логах только результат и время: «токен обновлён, действует до 14:32».
- **Статус** (`ready | unavailable`, причина без секретов) доступен как `tokens.status` и показывается на host (15.4). Причины кодируются короткими метками: `ssl`, `auth`, `timeout`, `network`, `error` (функция `describe_error`).
- **Время** берётся из подменяемой функции `now()` (для тестов).

**Эталонный каркас** (ориентир по поведению, не копировать слепо):

```python
import asyncio, random, time, uuid
import httpx


class TokenUnavailable(Exception):
    """Token cannot be obtained right now (message contains no secrets)."""


class TokenManager:
    REFRESH_MARGIN = 120   # start proactive refresh this many seconds before expiry
    HARD_MARGIN = 30       # below this the token is treated as expired
    COOLDOWN = 5           # after a failed refresh, fail fast for this many seconds

    def __init__(self, http: httpx.AsyncClient, oauth_url: str, auth_key: str,
                 scope: str, now=time.time):
        self._http, self._url, self._key, self._scope, self._now = http, oauth_url, auth_key, scope, now
        self._token: str | None = None
        self._expires_at = 0.0                 # epoch seconds
        self._lock = asyncio.Lock()
        self._last_attempt = 0.0
        self._task: asyncio.Task | None = None
        self.last_error: str | None = None     # short label, no secrets

    def __repr__(self):
        return f"TokenManager(ready={self.is_ready})"   # never print the token

    def _remaining(self) -> float:
        return self._expires_at - self._now()

    @property
    def is_ready(self) -> bool:
        return self._token is not None and self._remaining() > self.HARD_MARGIN

    async def start(self):
        try:
            await self.refresh(force=True)
        except TokenUnavailable:
            pass                               # the app still starts, status shows the reason
        self._task = asyncio.create_task(self._refresher())

    async def stop(self):
        if self._task:
            self._task.cancel()

    async def get_token(self) -> str:
        if self.is_ready:                      # fast path: no network, no lock
            return self._token
        await self.refresh()
        if not self.is_ready:
            raise TokenUnavailable(self.last_error or "no token")
        return self._token

    async def invalidate(self, bad_token: str):
        if self._token == bad_token:           # only if it is still the current one
            self._expires_at = 0.0
        await self.refresh()

    async def refresh(self, force: bool = False):
        seen = self._token
        async with self._lock:                 # single-flight
            if self._token != seen and self.is_ready:
                return                         # somebody refreshed while we were waiting
            # +10: the background task wakes up REFRESH_MARGIN + jitter (<= 10 s) before expiry
            if not force and self.is_ready and self._remaining() > self.REFRESH_MARGIN + 10:
                return
            if self.last_error and self._now() - self._last_attempt < self.COOLDOWN:
                raise TokenUnavailable(self.last_error)          # fail fast
            self._last_attempt = self._now()
            try:
                self._token, self._expires_at = await self._fetch()
                self.last_error = None
            except Exception as e:
                self.last_error = describe_error(e)              # "ssl" | "auth" | "timeout" | ...
                raise TokenUnavailable(self.last_error) from e

    async def _fetch(self) -> tuple[str, float]:
        r = await self._http.post(
            self._url,
            headers={"Authorization": f"Basic {self._key}",
                     "RqUID": str(uuid.uuid4()),
                     "Accept": "application/json"},
            data={"scope": self._scope},       # httpx sets application/x-www-form-urlencoded
            timeout=httpx.Timeout(10.0, connect=4.0),
        )
        r.raise_for_status()
        d = r.json()
        exp = float(d["expires_at"])
        if exp > 1e11:
            exp /= 1000.0                      # milliseconds -> seconds
        if not (self._now() < exp < self._now() + 3600):
            exp = self._now() + 25 * 60        # sanity fallback
        return d["access_token"], exp

    async def _refresher(self):
        backoff = 5
        while True:
            try:
                if self.is_ready:
                    delay = self._remaining() - self.REFRESH_MARGIN - random.uniform(0, 10)
                    await asyncio.sleep(max(delay, 1))
                await self.refresh()
                backoff = 5
            except asyncio.CancelledError:
                raise
            except Exception:
                await asyncio.sleep(backoff)
                backoff = min(backoff * 2, 60)
```

### 15.3. GigaChatClient

Модуль `app/dealer/gigachat_client.py`, реализует `LLMClient`.

- **Запрос:** `POST {GIGACHAT_API_BASE}/chat/completions`, заголовок `Authorization: Bearer <токен из get_token()>`. Тело: `model`, `messages` (**одно** system-сообщение первым, затем user), `temperature`, `max_tokens`. Для JSON добавляется `response_format: {"type": "json_schema", "schema": <схема>}`. Ответ читается из `choices[0].message.content` (при `json_schema` это JSON-строка, разбирается через `json.loads`). Точный формат сверить с актуальной документацией GigaChat.
- **Обработка 401** (каркас):

```python
async def _chat_request(self, payload: dict) -> dict:
    for attempt in (1, 2):
        token = await self.tokens.get_token()          # TokenUnavailable -> резервный контент
        r = await self.http.post(f"{self.base}/chat/completions", json=payload,
                                 headers={"Authorization": f"Bearer {token}"})
        if r.status_code == 401 and attempt == 1:
            await self.tokens.invalidate(token)        # одно обновление (single-flight), затем повтор
            continue
        r.raise_for_status()
        return r.json()
```

- **Очередь:** `asyncio.Semaphore(1)`, потому что в бесплатном режиме генерация идёт в один поток.
  - `priority="high"` (задания, штрафы, взятки, выбор события) ждёт очереди до 8 секунд.
  - `priority="low"` (комментарии) выполняется, только если очередь свободна, иначе пропускается с `LLMUnavailable("busy")`.
- **Повторы:** таймаут запроса 8 секунд. При 429, 5xx и сетевых ошибках одна повторная попытка через 1 секунду для `high`, без повторов для `low`. Если не вышло, `LLMUnavailable`.
- **Бюджет токенов:** суммировать `usage.total_tokens` (если поле есть в ответе) в счётчике партии. При превышении `GIGACHAT_TOKEN_BUDGET` запросы `low` отключаются. Запросы `high` продолжаются до 120% бюджета, затем всё уходит на резервный контент. Расход показывается на host.
- **Валидация:** JSON проверяется по pydantic-схеме, при невалидном ответе одна повторная попытка, затем резервный контент.
- **Не блокировать игру:** вызовы идут через `asyncio.create_task`, результат подмешивается, когда пришёл.
- **Приватность:** в промпты не попадают карманные карты, фото не отправляются.

### 15.4. Проверка при старте и в лобби

- При старте сервера, если ключ задан: получить токен, запросить `GET {GIGACHAT_API_BASE}/models`, вывести в консоль статус и проверить, что `GIGACHAT_MODEL` есть в списке (если нет, предупреждение и список доступных моделей).
- В лобби host: индикатор «ИИ-судья: готов / недоступен (причина)», расход токенов за партию и кнопка «Проверить ИИ» (повторяет проверку).
- Понятные сообщения об ошибках:

| Ситуация | Сообщение |
|---|---|
| Сертификат не проверен (`ssl`) | «Нет сертификата Минцифры: положите файл в `certs/russian_trusted_root_ca.pem` (см. README)» |
| 401/403 при получении токена (`auth`) | «Неверный ключ авторизации или scope» |
| Таймаут или нет сети (`timeout`, `network`) | «Нет соединения с GigaChat, играем на резервном контенте» |
| 429 или лимит | «Лимит запросов, ИИ временно на паузе» |
| Модель не найдена | «Модель X недоступна, доступны: ...» |

**Два разных сертификата не путать:** `mkcert` нужен для HTTPS-сервера, к которому подключаются телефоны, а корневой сертификат Минцифры нужен только для **исходящих** запросов к GigaChat. Файл Минцифры передаётся только в `httpx`-клиент GigaChat (`verify=...`), проверку сертификатов в остальном процессе не отключать и не менять.

### 15.5. Тесты (`tests/test_token_manager.py`, без реальной сети)

Использовать `httpx.MockTransport` и управляемые часы (`now()`):
1. первый `get_token()` получает токен, второй вызов не делает сетевого запроса;
2. 20 одновременных `get_token()` при пустом кэше дают ровно **один** запрос к OAuth;
3. фоновая задача обновляет токен за `REFRESH_MARGIN` до истечения (на ускоренных часах);
4. 401 от API → одно обновление → повтор запроса → успех;
5. 10 одновременных запросов с 401 → ровно **одно** обновление токена;
6. `expires_at` в секундах и в миллисекундах приводится к одному результату;
7. ошибка OAuth → `TokenUnavailable`; вызовы в течение `COOLDOWN` не создают сетевых запросов; после `COOLDOWN` попытка повторяется;
8. при недоступном токене игра не падает и берёт резервный контент;
9. в логах, исключениях и `repr` нет ключа и токена.

### 15.6. Общие требования к ИИ

- Промпты лежат в `app/dealer/prompts.py`: роль (весёлый судья за покерным столом), ограничения безопасности (раздел 9.2), острота из настроек, краткий контекст игры (стеки, последние 3 раздачи, события). Личные карты игроков в контекст **не передаются**. В запросе одно system-сообщение.
- Все ответы ИИ валидируются, для каждой функции есть резервный контент в `data/`.

## 16. Безопасность, приватность, надёжность

- **Античит:** вся логика на сервере; клиент отправляет только намерения. Сервер проверяет, что действие допустимо (чей ход, допустимая сумма, способность есть в руке и т.д.).
- **Токены:** случайные, одноразовые для присоединения (`dealer`, `players` токены), сессионные для переподключения. QR диллера гаснет после подключения.
- **Фото:** только `image/jpeg|png|webp`, не более 8 МБ; сервер перекодирует в JPEG с длинной стороной 1024 px и **удаляет EXIF** (геометки). Хранение во временной папке `media_tmp/<room_id>/`. Все фото удаляются при закрытии комнаты (или через 24 часа), кроме сохранённых в альбом.
- **Согласие:** перед входом игрок явно соглашается на камеру, показ фото на общем экране и датчики. Без согласия задания с камерой ему не выдаются.
- **Ограничения частоты:** лимит сообщений на соединение (например, 20 в секунду) и на загрузку фото.
- **Логи:** структурное логирование действий (без карманных карт) в файл `logs/`.
- **Секреты ИИ:** ключ авторизации GigaChat и access token хранятся только на сервере (ключ в `.env`, токен в памяти), не попадают в логи, ответы клиентам и репозиторий. В окне согласия указано, что никнеймы игроков и ход раздач передаются во внешний ИИ-сервис (карманные карты и фото не передаются).
- **Отказоустойчивость:** отключение игрока не должно останавливать игру (авто-fold по таймеру), падение ИИ не должно ломать игру.

### 17.2. Этапы и критерии приёмки

**Этап 1. Каркас и подключение.** FastAPI + HTTPS, `run.py`, создание комнаты, QR-коды (диллер и игроки), лобби на host, вход по токенам, WebSocket, переподключение.
*Приёмка:* с двух телефонов можно войти по QR, имена видны на host, QR диллера одноразовый.

**Этап 2. Движок Hold'em.** `cards`, `evaluator`, `pots`, `engine` (блайнды, торги, side pots, таймеры, выбывание).
*Приёмка:* тесты на 30+ сценариев (комбинации, ничьи, all-in с несколькими side pots, heads-up); движок работает без сети.

**Этап 3. Играбельная классика.** Синхронизация состояния (`views.py`), экраны host и player, действия игроков, шоудаун, отрисовка карт кодом (раздел 11.4: лицо, рубашка, размеры, анимации раздачи и переворота).
*Приёмка:* полная партия классического покера с 3+ телефонами; карты выглядят одинаково на host и у игроков; тест подтверждает, что игрок не получает чужие карты.

**Этап 4. Карты Событий.** Каталог, хуки, окно вето, отображение на host.
*Приёмка:* по одному тесту на каждое событие; событие корректно отображается и влияет на раздачу.

**Этап 5. Способности и побочные ставки.**
*Приёмка:* каждая способность работает, личные результаты приходят только владельцу, побочный пул распределяется правильно.

**Этап 6. Судья-человек и текстовые задания.** Экран диллера, выдача заданий, штрафы, указы, пауза, режим без диллера (голосование).
*Приёмка:* судья может выдать задание, игрок его видит, host показывает результат.

**Этап 7. Фото-задания.** Камера, загрузка, обработка Pillow, проверка диллером, показ на host, реакции, альбом, удаление данных, банк резервных заданий.
*Приёмка:* полный цикл «задание → фото → проверка → показ» на реальных телефонах.

**Этап 8. Физические активности.** Датчики, подсчёт, разрешение на iOS, запасной ручной вариант.
*Приёмка:* работают шейк-баттл и «Замри», при отказе от датчиков активность подтверждается вручную.

**Этап 9. Судья-ИИ.** Сначала `TokenManager` (раздел 15.2) с тестами из 15.5, затем `LLMClient`, `GigaChatClient` (очередь, повторы, бюджет), проверка при старте и индикатор в лобби (15.4), после этого комментарии, выбор события из каталога, генерация штрафов и фото-заданий (для режима `human`), взятки, итоговый протокол, резервный контент.
*Приёмка:* все тесты `test_token_manager.py` проходят; на реальном ключе токен обновляется автоматически без вмешательства при игре дольше 60 минут; при отключённом интернете или ошибке токена игра идёт с резервным контентом без задержек; в режиме `ai` кнопка фото-заданий скрыта; в логах нет ключа и токена.

**Этап 10. Полировка.** Итоги игры, альбом (zip), звуки и анимации, вибрация, README с пошаговой установкой.
*Приёмка:* игру может запустить человек, следуя только README.
